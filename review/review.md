# Взаимное рецензирование по КТ3

## Проверка проекта «Создание виртуальных туров по объектам недвижимости»

Автор — Бабейко Софья Алексеевна, ИКБО-31-24. Рецензент — Цой Марат Андреевич, ИКБО-31-24. Дата проверки — 23 ноября 2026 г. [Проверенный коммит 1d7279f](https://github.com/babeyko/study_practice_5_sem/commit/1d7279fea3b52019532a27767c67034f9600f048)

Проект собрался командой `mvn clean package` на Maven 3.9.11 и JDK 25. На примере из README программа создала три сцены и опубликовала первую версию тура. При запуске Java и Python на одном входном файле все поля результата совпали, кроме времени публикации. Отдельно проверен пример с удалённым переходом из второй сцены в третью. Программа сообщила о недостижимой сцене, завершилась с кодом 2 и не создала выходной файл.

На UML и в коде два подкласса `Panorama` по-разному выбирают подпись сцены — из подсказки оператора или из имени файла. В `RoomMatcher` оба правила сопоставления вызываются через интерфейс `MatchingRule`. По коду легко проследить, почему точное совпадение получает три балла, а синоним — два. Для обхода графа `TourGraph` хранит соседей каждой сцены в списке, а уже посещённые сцены — в множестве. [Диаграмма классов](https://github.com/babeyko/study_practice_5_sem/blob/1d7279fea3b52019532a27767c67034f9600f048/models/classes.puml)

### Замечания

1. **При совпадении путей теряются исходные данные.** На копии примера один и тот же файл был передан в `--input` и `--output`. Программа завершилась успешно и заменила список помещений и панорам результатом публикации. Предлагаю до записи проверить, указывают ли пути на один файл, и вывести ошибку. Проверку стоит повторить для путей вида `input.json` и `./input.json`. [Main.java, строки 46–48](https://github.com/babeyko/study_practice_5_sem/blob/1d7279fea3b52019532a27767c67034f9600f048/src/java/src/main/java/tour/Main.java#L46-L48)
2. **К сцене можно привязать помещение из другого объекта недвижимости.** В примере у комнаты «Кухня» изменён только `property_id` со 101 на 202. Тур для объекта 101 всё равно получил статус `published`, а у первой сцены осталась ссылка на эту кухню. При подборе комнаты предлагаю учитывать `property_id` панорамы. Тогда при отсутствии своей кухни панорама получит уже предусмотренный статус `manual_review`. [RoomMatcher.java, строки 17–19](https://github.com/babeyko/study_practice_5_sem/blob/1d7279fea3b52019532a27767c67034f9600f048/src/java/src/main/java/tour/RoomMatcher.java#L17-L19)

## Полученная рецензия на AR-визуализатор

Рецензент — Бабейко Софья Алексеевна, ИКБО-31-24. [Проверенный коммит 0459877](https://github.com/mariikkkk/ar-music-visualizer/commit/045987714ec66abf5dd65e5f45cbfaa773c26a91)

> Проверила твой проект. Он собирается и запускается по README. На примере из README и при повторном анализе Java и Python дали одинаковые результаты в пределах указанного допуска. Время запуска не сравнивала.

### 1. Диапазон идентификаторов кадров

> Если у уже сохранённого кадра ID `2147483646`, Java присваивает второму новому кадру отрицательный ID и сохраняет JSON. При следующем запуске программа этот файл уже не принимает. Предлагаю проверять диапазон ID перед сохранением. `Model.java`, строки 49–54.

Исправлено в коммите `9d498c4`. Перед обработкой трека программа проверяет, хватит ли идентификаторов на все полные кадры. Для примера из 61 кадра проверены обе границы. При 61 свободном ID последний кадр получил 2147483647. При 60 свободных ID программа сообщила об ошибке и сохранила прежнее содержимое выходного файла.

### 2. Формат целочисленных полей

> Я поменяла во входном JSON `track_id` с `1` на `1.0`. Java приняла значение, а Python выдал ошибку. Предлагаю проверять формат целочисленных полей до преобразования, чтобы обе версии одинаково обрабатывали такой ввод. `InputJson.java`, строки 60–64.

Исправлено в коммите `fc12e7f`. Для целочисленного поля программа проверяет, что передано число JSON, и разбирает его исходную запись через `Integer.parseInt`. На одном и том же примере обе версии приняли число `1` и отклонили число `1.0` и строку `"1"`.

### 3. Хранение кадров на диаграмме классов

> На UML у `Dataset` показана связь с `Track`, а списки кадров анализа и визуализации видны только среди полей. Предлагаю добавить связи с этими классами или коротко пояснить на схеме, что кадры хранятся в `Dataset`, а к анализу и сеансу привязаны по ID. `Dataset.java`, строки 76–87.

Исправлено в коммите `99c35d0`. На диаграмму добавлено пояснение. Оба списка кадров хранит `Dataset`. Поле `run_id` связывает кадр анализа с запуском, а поля `session_id` и `frame_id` связывают визуальный кадр с сеансом и кадром анализа.
